### 2026-11-22（第七轮：4KHD 伪挑战修复）

用户反馈 4KHD 报“站点要求浏览器验证”。实测主机侧直连首页 **HTTP 200 / 102KB / 标题正常**——不是 Cloudflare 拦截。

- **根因**：`SiteHtml.challenge()` 的判定 `challenge-platform && length < 120000 && !</video>` 命中误判。4KHD 正常内容页里注入的是 Cloudflare **被动 JS 检测**（`/cdn-cgi/challenge-platform/scripts/jsd/main.js`），不是拦截页；页面 102KB < 120KB 阈值，于是每个页面都被当成挑战页 → 走镜像链 → 最终报“要求浏览器验证”。（另查 `/scss.js` 与 `/worker.js`，混淆脚本做的是 service worker 缓存清理，不含准入校验。）
- **修复**：判定改为必须有明确拦截证据才拒——标题级提示（Just a moment / Checking your browser）、`cf-mitigated`、DDoS-Guard 且无列表结构，或 `challenge-platform` **且页面无任何内容证据**（无 `</video`、无 `.thumbs`、无 article/entry-title/wp-content/main/video-card 等 CMS 容器）。
- 新增 `SiteHtmlTest.passiveCloudflareInjectionOnARealPageIsNotAChallenge`：正常内容页不拦、真拦截页拦、空壳仍拦。305 项 JVM 通过。
- **设备实测**：模拟器切 4KHD，首页 Hero 与瀑布流正常加载（此前报“站点要求浏览器验证”）。
- 附带收益：所有带 Cloudflare 被动 JSD 的站点（MissAV / Jable / Pornhub 等）都不再可能被这条启发式误判。

### 2026-11-22（第九轮：失效页地址自愈）

上一轮设备验收发现：带旧阅读进度的写真集打开报“无法识别 Cosplaytele 图片地址”。

- **根因**：`loadStripPage` 的地址优先级是 `下载页缓存 → 已渲染页 → 相邻页 next/prev → 阅读进度记录 → 站点重新解析`。前几项来自历史记录，站点改版或内容重排后即失效，而失效地址会一直胜出、永不重新解析——每次打开都报同一个错。

### 2026-11-22（第十轮：全项目检查后的缺陷修复）

用户要求“全项目检查”，逐文件静态审计后修复。分级为 P0（正常路径不可用）、P1（功能正确性）、P2（低风险）。

**P0 —— 正常使用路径直接失败**

- **离线阅读器报“下载图页目录缺失”**（HEAD `cb69644` 引入的回归）：`loadStripPage` 里 `val fallback = if (offlineOnly) error(...)` 立即求值，`cached ?: …` 永远走不到。改为 `suspend fun resolve()` 按需解析；离线与命中已存映射时都不联网，顺带消除非离线场景下每页多打一次预览页请求。自愈重试只在失败地址来自缓存/进度记录、且非纯 IO 错误时触发（避免一次网络抖动丢掉全部页地址）。
- **本地视频导入后立刻打不开**：`addLocalVideo` 的第二个参数决定写入哪个站点分区，之前默认当前浏览站点，而 `play()` 只在 `local` 分区查。显式传 `SiteRegistry.LOCAL.id`。
- **登录凭据可能提交给错误站点**：`Network.login()` 读进程级 `SiteRegistry.current`，而对话框持有自己的站点。改为 `login(site, username, password)` 显式绑定，并在成功后写入该站点的用户名（Cookie 类登录此前不写 `native_username`，设置页因此无法退出）。

**P1 —— 功能正确性**

- `LibraryStore.readings()`：坏记录（Gson 把缺 `entry` 的记录填 null）此前会让整站阅读历史读不出来、连新进度也存不下。改为逐条容错并跳过；`removeReading` 读改写收进同一把锁，避免覆盖后台刚写入的进度。
- `PersonalStore.snapshot()`：解析失败静默回退空库，下一次编辑就会覆盖片单/书签/收藏。改为先把原文本另存为 `.corrupt.<ts>`（保留最近三份）再回退。
- `GalleryDownloadStore`：不带页码的 `add()` 不再沿用旧的 `selectedPages`（否则“继续保存/下载整本”永远只补原选页）；`repair()` 带页码时不再被 `isDownloaded()` 短路；`retryJobs.contains(id)`（`ConcurrentHashMap.contains` 是 containsValue 语义）改 `containsKey`，重试定时器改为条件写，不会把用户刚做的暂停改回排队；`next()` 用 `invokeOnCompletion` 回收 `active`，协程启动前被取消不再卡死整条队列。
