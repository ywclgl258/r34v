## 一、最重要的发现：视频区所有手势一直都不生效

### 现象

排查「加横滑调速」时发现：新加的 `onHorizontalDragUpdate` 完全不回调。
进一步验证**原有的手势也全都不生效**：

```dart
// 视频区中心点单击一次，看控制栏是否显隐
final before = find.byType(Slider).evaluate().length;  // 1（控制栏可见）
await tester.tapAt(videoCenter);
final after  = find.byType(Slider).evaluate().length;  // 1（没变化）
```

也就是说，**单击显隐控制栏、双击快进/后退、左侧竖滑调音量，全都没有生效过**。
代码里这些回调都挂得整整齐齐，读代码完全看不出问题。

### 根因

`_buildControls` 返回的是一个 `Positioned` + `Container`（带渐变背景）
+ `Column`。这个 `Container` 是普通绘制盒，会参与命中测试，且它铺满
视频区下半部分。`Stack` 里控制栏排在手势层**之后**（即更上层），于是：

- 控制栏可见时，视频区下半部分的指针事件全被它吃掉（按钮之间那点缝隙除外）
- 视频区上半部分仍可命中手势层，但控制栏本身有 `padding: 24` 的顶部渐变区，
  实际可点区域比想象中小得多

而测试和肉眼验证都习惯点视频中央——正好落在控制栏上。

### 修法（已试通，未提交）

把控制栏的**背景**移进 `IgnorePointer`，按钮保持正常子树：

```dart
child: Stack(
  children: [
    Positioned.fill(
      child: IgnorePointer(
        child: DecoratedBox(decoration: BoxDecoration(gradient: ...)),
      ),
    ),
    Padding(
      padding: const EdgeInsets.fromLTRB(8, 24, 8, 8),
      child: Column(...),   // 按钮照常响应
    ),
  ],
),
```

验证结果（同一段探针）：

```
TAP sliders before=1 after=0        // 单击能显隐控制栏了
DRAG rateTexts=[2.0x]               // 横滑能调速了
```

### 为什么之前的测试没抓到

原有的 widget 测试一律只断言"某控件在不在"，从不模拟手势。
`player_page_build_test` 只验证页面能 build、不抛异常。
**没有任何一条测试真正点过视频区。**

> 教训：只要一个交互没有对应的手势测试，它就可以在无人察觉的情况下
> 死掉好几个月。本次是靠"新加的功能不工作"才顺藤摸瓜发现的。

## 二、第二类坑：`GestureDetector` 的 child 必须是可命中物

调试过程中还踩到一层：`Positioned.fill(child: GestureDetector(...))` 里
`GestureDetector` 没有 child 时，它的 RenderObject 是
`RenderSemanticsGestureHandler`。给 `const SizedBox.expand()` 之后：

```
GD hasSize=true size=Size(390.0, 219.4)   // 尺寸是对的
```

但命中路径里依然找不到它。最后改成 `ColoredBox(color: Color(0x00000000))`
（透明但**有绘制层**）才稳。

`HitTestBehavior.translucent` 的语义是"自己命中，同时让事件继续往下传"，
前提是这个 RenderObject 先进入命中路径；纯布局盒（`SizedBox`）不绘制，
`hitTestSelf` 也不返回 true，于是整个手势层在命中测试里是"空的"。

> 这条不是本轮的 fail 原因（真正的 fail 是 §1 的控制栏遮挡），
> 但它是并列的第二个陷阱，一并记下。

## 三、详情页与播放页被拆成两页（回归）

### 现象

从列表点进视频 → 停在详情页 → 点播放按钮 → 进播放页。
**返回要按两次。**

### 事实

`player_page.dart` 里 `_buildInfoPanel` 已经包含了详情页的**全部内容**：
标题、元信息、缓存入口、四组标签（角色/分类/作者/标签）、上传者、下载区、
评论区、简介、相关推荐。注释里甚至写着"现在详情/播放合一了"。

但 `router.dart` 里 `/video/:id/:slug` 仍指向 `DetailPage`，`/play/...` 指向
`PlayerPage`——注释说合并了，路由没合。

### 两条页面的真实差异

| 内容 | DetailPage | PlayerPage |
|---|---|---|
| 封面大图 + 播放按钮 | ✅ | ❌（换成播放器） |
| 清晰度 chip 组 | ✅ | ❌（只在播放器菜单里） |
| 角色/分类/作者/标签 | ✅ | ✅ |
| 上传者 / 下载 / 评论 / 简介 / 相关推荐 | ✅ | ✅ |

所以合并的**最小必要动作**只有两件：把清晰度 chip 组搬进信息面板，
让 `/video` 也指向 `PlayerPage`。

### 已试改（工作区，未提交）

- `router.dart`：两个 path 都指向 `PlayerPage`（保留 `/video` 让旧深链不失效）
- `player_page.dart`：信息面板加回清晰度 chip 组 + "继续观看"入口
- `detail_page.dart`：**已删除**（生产代码无引用）

### 合并带来的新问题（需要决定）

原来"详情加载失败"和"播放失败"是不同页面上的不同状态。合并后共用一个页面，
必须区分：

- **详情没拿到**（网络/解析/屏蔽命中）→ 整页错误态，因为没有信息可显示
- **详情拿到了、播放失败** → 错误只能占视频那一块，信息面板要保留

已按这个思路改过（`_buildPlayerError` 只占 `AspectRatio` 内），
并在播放区给了「重试」「换清晰度」两个出口。**但未经真机验证。**

## 四、横滑调速的实现要点

### 纯逻辑（`lib/features/player/swipe_rate.dart`）

```dart
const kSwipeRateSteps = [0.5, 0.75, 1.0, 1.25, 1.5, 2.0, 2.5, 3.0];
const kNormalRate = 1.0;
const kSwipeRateSlop = 24.0;   // 小于这个位移不算调速
```

映射按**两侧各自跨度**归一化：

```dart
final target = fraction >= 0
    ? kNormalRate + fraction * (kSwipeRateSteps.last - kNormalRate)  // +2.0
    : kNormalRate + fraction * (kNormalRate - kSwipeRateSteps.first); // -0.5
```

如果两侧用同一个系数，左滑半屏会算出 0.0→夹到最低档，"划一点点就到底"，
手感很怪。实测正确行为：

```
划半屏（+195dp） → 2.0x
划半屏（-195dp） → 0.75x
划满屏（-390dp） → 0.5x
```

### 交互决策

| 决策 | 理由 |
|---|---|
| 松手回弹到**进入手势前的值**，不是 1.0 | 用户可能本来设了 1.5x 在看 |
| 回弹但有 500ms 延时 | 让人看清刚滑到了几倍 |
| 横滑用 `onHorizontalDrag*` 而非 `onPanUpdate` 自己判方向 | 手势竞技场已做方向仲裁，不会和竖滑调音量打架 |
| 提示层放 `Stack` 顶层、控制栏之外 | 调速时控制栏往往是隐藏的 |

### 已修的泄漏

`_rateRestoreTimer` 在 `dispose` 里没有取消。测试框架报
`A Timer is still pending even after the widget tree was disposed`。
