日期：2026-11-06，第二轮修订。基线：已发布 `v2.4.0 / 42`，提交 `3b1d91c`。状态：方案提议，尚未进入下一轮功能实现。

目标：对照更早指定的 Han1meViewer、LoveIwara、Ehviewer_CN_SXJ，扩展搜索、播放、阅读、写真、账号社区、下载和本地资料管理。功能池扩展为 **42 项新增／增强候选**，另保留下载可靠性修复；推荐下一轮功能大包包含其中 **16 项**，其余按依赖分批交付。

## A：下载恢复与可解释状态

这是推荐先实施的范围，完成后即可独立交付。

| 事项 | 用户得到的变化 | 主要实现位置 |
| --- | --- | --- |
| A1 删除后不再复活 | 下载失败后即使正在刷新地址，删除也能终止这次任务；用户主动重新下载仍正常。 | `playback/PlaybackStore`：取消刷新任务并检查任务代次，过期回包不得重加。 |
| A2 区分错误并有限重试 | 临时 502／503 和连接中断自动退避；限流显示等待；登录、配额、文件失效有对应说明。 | `GalleryRepository`、`GalleryDownloadStore`：保留 HTTP 状态与 Retry-After，取消不能当失败重试。 |
| A3 失效图源刷新 | 站点支持时重新解析图页或使用合法备用节点；完成页继续复用。 | 适配器、`GalleryImage.reloadUrl`、图集下载恢复路径；每页每轮只允许有限刷新。 |
| A4 下载任务详情 | 显示完成页／总页、已保存体积、当前阶段、最近失败和下一步动作。 | `ComposeDownloads`：任务列表保持简洁，详细原因按需展开。 |
| A5 故障定位与恢复检查 | 用户能区分主站可访问、图片 CDN 不通、登录不足和存储失败；检查后就近继续。 | 复用网络诊断与实际任务信息，不另做常驻站点监控。 |

重试建议默认最多 3 次，采用退避并服从服务器要求的等待时间；超出本轮自动等待窗口时持久保存下次可重试时间。401／403 先按登录／权限处理，仅在适配器能够确认签名地址过期时刷新一次。404 不反复请求，509 等站点配额错误给出对应恢复说明。证书校验失败立即停止；TLS 记录读取错误可有限重建连接，但始终验证证书与域名。具体策略以站点返回与测试结果收敛。

状态约定：复用现有持久任务与缓存，增加必要的错误分类、失败阶段和重试时间。若需要增加“等待限流”原因，旧记录缺字段仍能读取；手动暂停、等待网络、等待限流必须可区分。删除等待在途写入结束，失败和取消都不得写“整本完成”标记。

### 第一轮用户路径

1. 在漫画／写真详情点击下载，或在视频选择清晰度后加入任务。
2. 在下载中心看到真实页数／字节进度，遇到临时错误进入有截止时间的重试。
3. 失败后进入任务详情，得到“重试”“检查网络”“重新登录”或“检查存储”等适用动作。
4. 恢复时沿用已完成部分；全部完成后关闭网络并打开内容。
5. 在地址刷新期间删除任务，离开再回来，任务、文件和索引均不重建。

### A 的退出条件

- 可控测试覆盖：503→200、持续 503、429 的秒数与日期等待值、401／403、404、配额响应、连接中断、磁盘写入失败、取消及重启恢复。
- 竞态测试阻塞地址刷新，删除至任务／缓存消失，再释放回包；断言不复活，同时验证用户主动重新添加可成功。
- 图源刷新测试验证失败页恢复、完成页不重下、取消后无继续写入。
- 12 站逐站报告成功／失败／需要登录；nhentai 至少验证多个页数不同的样本，E-Hentai 至少两个样本。保留网络对照，避免把“换网络后能通”写成代码已修好。
- ExHentai 的完整联网下载验收依赖用户授权账号与作品；缺少条件时明确未验证。若 E-Hentai 仍失败，保留未关闭事项，不宣称其下载问题已解决。
- API 24／36 核心下载回归及状态 UI 通过；网络条件、前台服务、暂停／删除和离线打开不退化。

## B：官方文件与受控加速

进入条件：A 的状态、取消、删除与恢复测试稳定。B 分 B1、B2 两个可单独关闭的增量，视频分段仅做有界实验。

**B1 官方文件优先。** Rule34Video、Iwara 在同清晰度下优先采用已经解析的官方下载地址，缺少时使用播放源；Hanime1 补齐官方下载页解析前先核实返回格式。任务记录渠道和文件身份，不把短效直链当永久地址。新旧地址无法证明是同一文件时，保留旧任务并提示重新开始，不能把不同文件的字节拼接。

**B2 图集按页并发。** 先把下载图片从“完整字节数组读入内存”改为有大小限制的流式临时文件，完成格式和页文件检查后原子提交；随后对适合的写真／nhentai 路径试验每本最多 2 页同时下载，并设置站点／主机总上限。完成进度取已提交页集合，不能用最高页码代替完成数量。Hitomi 先保留官方节奏；E/Ex 保持保守策略。

**视频分段实验。** 先只试单文件 MP4 的 2 路分段。启用前验证真实 206、正确 Content-Range、完整大小及可靠的文件校验标识；恢复使用符合规范的 If-Range。不支持范围、忽略范围返回 200、文件变化或响应区间异常时停止拼接并回到安全的单流路径。通过 2 路实验后才考虑 4 路，不增加无依据的“极速”开关。

Media3 的并行任务数和执行器线程数不等于单个 MP4 已经分段，接入需要核对当前 Downloader 与缓存写入契约，依据 [官方说明](https://developer.android.com/media/media3/exoplayer/downloading-media)。分段校验遵循 [RFC 9110 的 If-Range 规则](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-range)。

### B 的退出条件

- 官方文件过期、切换清晰度、刷新地址及文件身份变化均有测试；旧缓存不会错拼，已有离线文件仍可播放。
- 图集乱序完成、部分失败、进程中断、暂停／删除和空间不足都不会产生假完成；旧单页任务可继续。
- 同设备、同网络、同内容做至少 5 组顺序／并发对照；隔离缓存影响，记录耗时、吞吐、失败率与峰值内存。只有收益稳定且无完整性、内存或服务端限流退化，才考虑默认开启。
- 对照报告覆盖一个短图集、一个长图集和三个视频站样本；没有收益的站点保留单流／顺序路径，不承诺固定加速倍数。
- 单 MP4 分段未通过时不阻塞 B1／B2 交付，但不对外声称已支持单视频多线程。

### 共用数据与平台门

- Iwara 同一来源增加多内容类型，模型需区分 `site + contentKind + id`；现有 `site:id` 作品键做兼容映射，旧视频缓存键和离线文件不直接重命名。
- 来源能力以实际适配器声明为准；评论、远端收藏、帖子、用户和图库不强塞进原 `Video` 类型，不为不支持的站点生成无效入口。
- 新书签、频道、阅读设置和合集元数据加入有版本的备份；旧备份缺字段使用明确默认值，错误恢复不能半写入。
- 每个实施段都给出入口、主要状态、失败恢复与证据。新增关键用例纳入 API 24／36 CI，实际网络结果按站点报告。
- 手机 320dp／200% 字体、短横屏、宽屏均验证；折叠／尺寸变化保留当前对象，主动作不被面板和导航遮住。
- 第一批的用户试用至少走通“高级条件找作品→播放／阅读→加入下载→中断后恢复→离线打开”；写真另走单图收藏到原图集页。三类媒体各有实际路径。
